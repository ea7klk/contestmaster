# API conventions

The REST API uses the `/api/v1` prefix. FastAPI publishes OpenAPI JSON at `/api/v1/openapi.json` and interactive documentation at `/api/v1/docs`; the schema is generated from typed request and response models.

## Error envelope

Errors have one stable JSON shape:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Request validation failed.",
    "request_id": "server-generated-or-accepted-id",
    "details": [{ "location": ["query", "page"], "message": "Input should be greater than or equal to 1", "type": "greater_than_equal" }]
  }
}
```

`details` is omitted when no field-level details apply. Unexpected server failures return a generic message and never disclose exception details. A request ID is accepted from `X-Request-ID` only when it contains 1–128 ASCII letters, digits, dots, underscores, colons, or hyphens; otherwise the server generates a UUID. The value is echoed in the response header and included in request logs.

## Collections

Collection endpoints use one-based `page` (default `1`) and `page_size` (default `50`, maximum `100`). Responses include `items` and `meta` with page, page size, total count, and page count. Collection handlers whitelist allowed `sort` fields per resource and use a deterministic unique key as a secondary sort; unknown sort fields are rejected. `order` is `asc` or `desc`. Filters are explicitly documented per collection, use exact-match semantics unless an endpoint documents another operator, and combine with AND. Stable pagination requires a stable sort; use cursor pagination only if a future collection's update volume needs it.

## Authentication boundary

Privileged accounts use `POST /api/v1/auth/login`, `/logout`, and `GET /api/v1/auth/me`. Login uses email/password and issues an opaque server-side session in an `HttpOnly`, `SameSite=Strict` cookie. Mutating authenticated requests require the matching `X-CSRF-Token` header. Global Administrators can list, create, edit, enable, and disable users through `/auth/admin/users`; they can create both Global Administrator and Contest Admin accounts, and list/update participant account status through `/auth/admin/participants`. The API prevents disabling or demoting the last active Global Administrator. Privileged password recovery uses `/auth/forgot-password` and `/auth/reset-password` with one-time, expiring tokens; successful reset revokes existing sessions.

`/api/v1/contests` supports authenticated, paginated contest listing and create/read/update operations. Contest Admin access is scoped to resources owned or assigned to the account; the original owner retains permanent ownership and alone (or a Global Administrator) may assign/revoke additional admins. A foreign contest ID is reported as not found. Global Administrators can view all contests. The same owner/assigned-admin authorization applies to contest operations and result generation. Ruleset roots retain their creator as permanent owner, with additional admins assigned through `/api/v1/rulesets/{ruleset_id}/administrators`. New contests start in `draft`; status publication transitions and results are separate operations. Contest configuration owns UTC start/end instants, optional periodicity, and the separate submission cutoff. Recurring contest records are editions attached to a `contest_series` row; the initial contest is its anchor. See [recurring contest behavior](../recurring-contests/README.md). `POST /api/v1/contests/import` accepts an atomic JSON package with `contest` metadata and a schema-version-2 `ruleset` draft; it creates an owner-assigned draft, validates active band/mode keys, and assigns the saved ruleset in one transaction. A failed import leaves neither a contest nor a newly saved ruleset behind.

`DELETE /api/v1/contests/{contest_id}` permanently deletes the contest and all contest-owned logs and dependent records, including revisions, QSOs, adjudication, score runs, published snapshots, receipt grants, submission idempotency records, ruleset activations, master-data pins, and private contest notes. The request body must contain the exact `confirm_slug`; the API still checks owner/global-admin access, and the deletion plus audit event is atomic. Shared participant identities and append-only global audit events are retained. Append-only and result-retention triggers remain in force during normal operation; the ORM inserts a transaction-scoped deletion permit for the authorized contest, and database guards allow deletion only for history rows owned by that contest. The permit disappears with the contest. A structurally invalid cross-contest adjudication reference or any other retained FK causes a conflict and rolls back the complete deletion.

Contest creation never accepts an owner identity from the request; the API assigns the authenticated account. All mutating privileged operations require both a valid session and CSRF token. Contest-scoped score-run review, QSO decisions, and Phase 8 result publication require the owner or a global administrator.

Contest Admins and Global Administrators can review submitted logs from the contest management page. `GET /api/v1/contests/{contest_id}/entries` returns a paginated list of entries for that contest, newest submission first, with optional case-insensitive `search` over callsign and entry key. `GET /api/v1/contests/{contest_id}/entries/{entry_id}` returns the selected (latest by default) immutable revision, its revision history, and paginated parsed QSO details; `revision_id` selects an older revision. `GET /api/v1/contests/{contest_id}/entries/{entry_id}/revisions/{revision_id}/download` returns that exact original uploaded file. Every endpoint enforces owned or assigned contest access (or Global Administrator access), returns 404 for entries outside the requested contest, and omits participant email addresses, receipt secrets, and other private access data. These manager review endpoints are separate from public standings and participant receipt workflows.

Public endpoints (health, published contest listings and published results) are explicitly unauthenticated. Guest log submission and entry receipt access are intentionally public/token-scoped workflows, not privileged accounts.

Participant account endpoints include `POST /participants/auth/register`, `/login`, `/forgot-password`, `/reset-password`, `/email-change`, and `/confirm-email-change`; `POST /callsigns` adds a secondary callsign and `DELETE /callsigns/{callsign_id}` removes a secondary callsign. `PATCH /me` updates the participant display name. Registration starts with an unverified account and sends a 15-minute single-use email link. Password login is rejected until verification. Password-reset tokens expire after 30 minutes, are stored only as hashes, and revoke existing sessions after use. Email changes require independent confirmations at the old and new addresses before the primary email is switched. Existing `/request-link` and `/consume-link` magic-link access remains supported. `GET /participants/auth/me` and `/entries` expose only the participant's identity and entries. Mutating account actions require the participant CSRF cookie/header pair except one-time bearer confirmation endpoints. Participant sessions are separate from staff sessions; they never grant Contest Admin or Global Administrator permissions.

Contest and ruleset owners can list and change assigned Contest Admins through `/contests/{contest_id}/administrators` and `/rulesets/{ruleset_id}/administrators`. The list response includes the permanent owner, assigned administrators, and eligible active Contest Admin accounts. Owners cannot remove themselves; Global Administrators may manage assignments on any resource. Assignment changes are written to the audit log. Assigned administrators can perform the same scoped resource operations as the owner but cannot change assignments unless they are also the owner or Global Administrator.

Global administrators manage master-data history through `GET /api/v1/admin/master-data/versions` and `/sync-runs`, `POST /versions/{version_id}/activate`, and `DELETE /versions/{version_id}`. Every route requires a global-administrator session; mutations also require CSRF. Version records include effective dates, source/run provenance, checksum, status, no-change sync outcomes, and contest/score-run/QSO reference counts. Activation accepts only successful candidate runs. Deletion accepts only candidate/retired versions with no retained references, removes the snapshot rows but retains sync/audit history, and is protected by both API checks and database foreign-key/active-version constraints. Activation and deletion may include an optional `audit_reason` query parameter.

Contest managers may change an owned contest through `draft → open → closed → published`; a closed contest may be reopened, and a published contest may be withdrawn to closed. Opening or publishing requires a saved ruleset that still validates. `GET /api/v1/public/contests` lists published contest metadata. `GET /api/v1/public/contests/upcoming` lists public `open` contests whose end instant is later than the response's `as_of` UTC instant; it includes currently running contests and excludes contests ending exactly at `as_of`. `GET /api/v1/public/contests/{slug}` exposes details for `open` and `published` contests only. Draft and closed contests are never returned through these public routes. The contest's nullable `description` field is Markdown source authored by its manager and is included in public details. The frontend renders it using a Markdown parser and HTML sanitizer. Public details also include the separate UTC log-submission cutoff and the validated declarative configuration of the contest's selected ruleset; the frontend uses that configuration to generate a plain-language overview. This generated overview may be imprecise and does not replace the sponsor's official published rules. The public ruleset configuration contains no participant data, uploaded logs, or internal adjudication notes.

After an entry exists, its manager may call `PUT /api/v1/contests/{contest_id}/entries/{entry_id}/access-grant` with `operation` set to `create`, `set_expiry`, `revoke`, or `rotate`. Grant expiry is optional and must be a timezone-aware future instant when set. Create and rotate return an opaque `receipt_token` once; only its SHA-256 digest is retained. The route verifies both contest ownership and that the entry belongs to that contest. These operations are audited without storing the secret token.

## Log submission and entry corrections

- `GET /api/v1/public/submittable-contests` lists open contests whose submission cutoff is in the future, with each contest's enabled `accepted_formats`.
- `POST /api/v1/public/contests/{contest_slug}/logs` accepts a multipart `file` plus required `Idempotency-Key`. It supports UTF-8 Cabrillo 2.0/3.0 and legacy unversioned marker files (`.log`, `.cbr`, `.cabrillo`, `.txt`) and text ADI/ADIF (`.adi`, `.adif`), up to 5 MiB. The contest's selected ruleset must explicitly enable the uploaded format; a missing ruleset or a ruleset with no currently supported format does not allow uploads. This server check is authoritative even if a client bypasses the browser's contest-specific file chooser filter. Cabrillo requires exactly one matching `CALLSIGN` and `CONTEST` header; ADIF QSO records use standard station, UTC timestamp, callsign, mode, band/frequency, and exchange fields. See the [supported-format guide](../formats/README.md) for field mappings and limits.
- The API limits full multipart requests to 5 MiB plus 64 KiB overhead. Log creation and full-log resubmission have no application rate limit; upload filenames are reduced to safe basenames and never used as filesystem paths.
- Valid submissions create participant/entry records without a privileged account, an entry-scoped receipt grant, an immutable first revision, station and QSO rows in one ORM transaction. A supplied email matching an existing participant email links to that participant; new addresses remain unverified until the email magic-link flow confirms them.
- Idempotency keys are stored only as SHA-256 digests scoped to the contest. Repeating the same key and file returns the same entry and same deterministic receipt token; using that key for different content returns `409`. In production, `ENTRY_RECEIPT_SECRET` must remain stable and contain at least 32 random bytes. Receipt tokens are returned to the submitter, while persistence stores only their digest.
- After acceptance, the response includes `guest_email_prompt_required`: it is true for ADI/ADIF logs and Cabrillo logs without a valid `EMAIL` header. Invalid Cabrillo email headers are warnings and do not reject otherwise valid logs. A valid Cabrillo `EMAIL` header initiates entry-access verification only; result notices are never inferred from that field.
- `POST /api/v1/public/entries/{entry_id}/guest-email` accepts `{ "email": "...", "entry_access": true|false, "result_notifications": true|false }` and requires the entry receipt (or associated verified participant session). At least one use must be selected. The response never echoes the address or verification token. Revoke both choices by sending the same address with both booleans false. Requests are rate limited.
- `POST /api/v1/public/entries/{entry_id}/guest-email/resend` replaces the outstanding verification token and sends a fresh link, subject to a stricter resend limit. `POST /api/v1/public/guest-email/verify` accepts `{ "token": "..." }`; tokens are SHA-256 hashed at rest, expire after 24 hours, and are single-use. Entry-access consent creates a grant scoped to this entry; result-only consent does not grant entry access. Receipt-token access remains available independently.
- After a public result snapshot is committed, one de-duplicated outbox event is queued for each selected entry with a verified address and result-notice opt-in. The email links to the public contest results and includes no score details, logs, QSOs, or review data. Delivery attempts retry with increasing delays up to six attempts; failures retain only a safe exception class in the outbox and logs. Repeated dispatch of sent/cancelled events is a no-op. `EMAIL_SMTP_HOST` and `EMAIL_FROM_ADDRESS` must be configured to deliver. Email sending never rolls back an accepted log or a published result snapshot.
- The frontend sends its selected UI language in `Accept-Language` on API requests. Transactional account and guest-verification messages use the supported base locale (`en`, `de`, `fr`, `es`, or `it`), falling back to English. The guest email-consent record stores the selected locale for asynchronous publication notices. Messages include localized subject/body text and a branded HTML alternative with a plain-text fallback.
- Malformed files return HTTP `422` with line-scoped error codes and messages. Rejected input creates no participant, entry, or QSO rows. Warnings and unmapped categories are reported separately. Unknown headers and extra QSO fields are retained in revision metadata.
- Parsing and validation finish before the short persistence transaction begins. The exact UTF-8 input text, content digest, safe filename, import metadata, and normalized contacts are stored in ORM-managed revisions and child records. Each revision records whether it came from public submission, an entry receipt, or a verified participant session; participant revisions reference the verified email identity without storing session or receipt secrets.
- `GET /api/v1/public/entries/{entry_id}` and the entry correction/contact routes require a valid `X-Entry-Receipt` token or a verified participant session associated with the entry. Participant mutations also require the participant CSRF token. Invalid or expired grants do not reveal whether an entry exists.
- `PUT /api/v1/public/entries/{entry_id}/log` appends a full resubmission only in a supported format enabled by that contest's selected ruleset, using `Idempotency-Key`. The authorized entry response includes the supported formats so the revision upload form can filter file selection. `POST /contacts`, `PUT /contacts/{contact_id}`, and `DELETE /contacts/{contact_id}` append contact changes as new immutable revisions. Contact IDs apply only to the current revision; prior revisions remain available for reproducibility.
- Managers may set grant expiry, revoke access, or rotate a receipt token through the contest access-grant endpoint above. Receipt secrets and idempotency keys are never written to logs.
- When `auto_recalculate_on_upload` is enabled, a successful new submission or full-log resubmission triggers scoring only after the accepted revision commits. Rejected requests and idempotent replays do not create another run. Upload responses include run IDs and statuses; scoring failures do not invalidate an accepted log.
- `GET /api/v1/contests/{contest_id}/score-runs` lists claimed, provisional, and adjudicated integer scores, input digest, status, timestamps, and failure details for the contest owner or a global administrator.
- `GET /api/v1/contests/{contest_id}/score-runs/{score_run_id}` returns that run with its per-QSO credited/status result, integer points/bonuses/penalties, multiplier keys, reason codes, and explanation. Both score-run endpoints require contest ownership and return `404` for foreign contest/run references.
- `POST /api/v1/contests/{contest_id}/qsos/{qso_id}/decisions` appends a manual decision. Its JSON body has `status` (`credited`, `not_credited`, or `needs_review`), `reason_code`, `reason`, and optional JSON `evidence`. The API stores reviewer and UTC timestamp, links the new row to the superseded decision, audits the change, then recalculates against that decision. Decisions and completed score runs are append-only.

## Result review, publication, and public standings

- `POST /api/v1/contests/{contest_id}/results/generate` requires manager/global-admin access and an `Idempotency-Key`. It reruns scoring for the contest and returns run IDs plus unresolved review items. `GET /api/v1/contests/{contest_id}/results/review` returns candidates, policy, and unresolved items for the authorized manager workspace.
- `POST /api/v1/contests/{contest_id}/results/publish` accepts `score_run_ids` and an optional audit reason. Only closed or already published contests can publish. Each selected run must be the latest completed run for its entry and match the current input revision. Publication atomically creates a sealed, immutable numbered snapshot and makes the contest public. Withdrawing a published contest returns it to closed; publishing again appends a new snapshot.
- Publication policy defaults exclude withdrawn entries and withhold late, checklog, and unresolved entries. Reclassified and disqualified entries are included with explicit status by default; disqualified score is zero and unranked. A declarative `result_publication` workflow hook can set boolean `include_late`, `include_checklog`, `include_needs_review`, `include_reclassified`, and `include_disqualified` values. No public response contains raw QSOs, private log files, participant contact details, or internal review notes.
- `GET /api/v1/public/contests` is unauthenticated and paginated; it lists only currently published contests. `GET /api/v1/public/contests/upcoming` is unauthenticated and paginated; it lists `open` contests until their end instant, including those currently in progress, and returns the UTC comparison instant as `as_of`. `GET /api/v1/public/contests/{slug}` returns details for open or published contests, never draft or closed contests. `GET /api/v1/public/contests/{slug}/results` returns the latest immutable snapshot with `page`, `page_size`, `sort` (`placement`, `score`, `callsign`, `status`), `order`, configured `category`/`value`, `band`, `mode`, and result `status` filters. Unknown category dimensions/values are rejected. The response includes aggregate score explanation, category values, status, available filters, publication number/digest, and pagination metadata.
- `GET /api/v1/public/contests/{slug}/results/entries/{result_entry_id}` returns one public-safe snapshot row. `GET /api/v1/public/contests/{slug}/results/export?format=json|csv` downloads the full publication as deterministic `results-v1` JSON or CSV and sets `X-Contestmaster-Export-Version: results-v1`. Sponsor-specific exports are deferred until an initial contest requires and defines one.
- `GET /api/v1/public/entries/{entry_id}/revisions/{revision_id}/download` downloads the exact original Cabrillo or ADI/ADIF revision. It requires that entry's valid receipt token or associated verified participant session; it is not a public result download. Managers can review original logs through the existing manager entry workflow.

## Ruleset authoring

`GET /api/v1/contests` and `GET /api/v1/rulesets/versions` return paginated manager lists using `page` and `page_size` with pagination metadata. Both accept an optional case-insensitive `q` search: contest name, slug, or an exact status; ruleset key, version, or source edition. The Vue manager pages use these endpoints to search and page the contest and saved-ruleset listings.

The graphic ruleset composer configures reusable contest rules and does not contain event start/end instants, recurrence, or the submission cutoff. Contest create/update and import requests carry those values as contest configuration; all event timestamps are UTC instants. See [Ruleset composer guidance](../ruleset-composer/README.md) for contest scheduling, category, exchange, eligibility catalog, scoring, and format explanations. Active band and mode choices are available separately at `GET /api/v1/rulesets/bands` and `GET /api/v1/rulesets/modes`. Global administrators manage them through `/api/v1/rulesets/admin/bands` and `/api/v1/rulesets/admin/modes`; managers cannot modify these catalogs. Eligibility keys must refer to active catalog items when a ruleset is validated or saved. Catalog edits are audited, and referenced keys cannot be renamed or deleted (deactivate them instead). The combined `/operating-catalog` read and admin write routes remain as compatibility adapters.

`POST /api/v1/contests/schedule-preview` accepts `periodicity`, UTC `starts_at`/`ends_at`, and optional series exceptions. It returns the next five non-skipped occurrences as UTC ISO 8601 instants, preserving event duration; the single-year `starts_at`/`ends_at` fields remain for compatibility. Recurrence patterns include annual date, nth weekday, and first/last/Nth full weekend. Invalid pattern shapes return 422.

Contest creation/update accepts `cutoff_offset_seconds`, `cutoff_is_override`, and `automatic_window_days` for recurring schedules. The UI constrains offsets to whole hours or days. An omitted rolling window disables automatic edition creation. `GET /api/v1/contests/series/{series_id}/exceptions` lists exceptions; authenticated owner/global-admin `POST` adds a `skip` or `move` exception, and `DELETE /api/v1/contests/series/{series_id}/exceptions/{occurrence_date}` removes it. A skip cannot delete an edition containing logs. `DELETE /api/v1/contests/series/{series_id}` requires a body containing the exact `confirm_name` and deletes every edition and dependent record atomically. The internal API timer materializes drafts at startup and hourly when `CONTEST_SCHEDULER_ENABLED` is true; `CONTEST_SCHEDULER_INTERVAL_SECONDS` controls the interval (minimum 60 seconds).

- `GET /api/v1/rulesets/catalog` returns the typed schemas, labels, and execution expectations for the built-in rule types used by the graphical composer.
- `POST /api/v1/rulesets/validate` accepts a proposed declarative ruleset but does not save or activate it. A valid response includes the normalized metadata, configured rule-type list, readable summary, and integer-only worked formula example. Invalid configurations return the standard error envelope with rule paths and messages.
- Category dimensions and choices may include optional plain-text `description` values (up to 800 and 600 characters respectively). These fields are stored in the immutable ruleset JSON, so older definitions remain valid; the public contest overview uses the descriptions and retains sponsor rules as authoritative.
- `GET /api/v1/rulesets/versions` lists immutable saved versions for authenticated administrators and managers, with `can_delete` indicating whether the viewer is the creator or a global administrator. `POST /api/v1/rulesets/versions` stores a validated version, is idempotent for identical content, and rejects attempts to reuse a key/version with different content.
- `DELETE /api/v1/rulesets/versions/{version_id}` deletes an unused version when the creator or a global administrator confirms its exact `ruleset_key@version`. The API returns `409` while any contest assignment, contest activation history, or score run references the version. The ORM service checks those references and inserts a transaction-scoped version deletion permit; the SQLite guard still blocks direct deletes. Successful deletion is audited; versions cannot be edited in place.
- `GET /api/v1/rulesets/versions/{version_id}` returns a saved immutable definition to authenticated administrators and managers so the graphic composer can load it for editing. Editing creates a new version; this endpoint and the composer never mutate the original version or change a contest's current assignment.
- `PUT /api/v1/contests/{contest_id}/ruleset` activates a saved version for a draft contest. The API checks contest ownership, revalidates the immutable version, and appends activation provenance. Managers cannot activate rules for another manager's contest.
- `PUT /api/v1/contests/{contest_id}/status` changes a contest's lifecycle status under the manager's ownership scope. The manager page exposes opening a draft after a valid ruleset is assigned, closing an open contest, and reopening a closed contest. Open contests appear in the public upcoming/current feed until their end time; drafts remain private.
- Administrative account creation, contest creation/updates/status changes/deletion, ruleset version creation/activation/deletion, entry receipt-grant changes, and master-data version activation/deletion append `audit_events` in the same ORM transaction as the operation. Events include the acting account where present, UTC occurrence time, target, request ID, safe allowlisted metadata, and an optional reason. Audit rows are protected against update and delete by database triggers.
- Conditions use the declared compare/all/any/not expression tree. The API rejects unknown fact paths and unsafe regular-expression features; it never evaluates submitted Python or JavaScript.
- `EligibilityRule.eligible_if` is a positive QSO predicate over configured contact geography, entry categories/declarations, exchanges, and station callsign. A contact that fails this predicate follows the rule's explicit `not_credited` or `needs_review` action.
- Cross-log matching runs only when the ruleset has a `workflow_hook` at stage `cross_log`. It compares reciprocal normalized callsigns, band/mode when present on both logs, UTC timestamps, and swapped exchange values. Optional `timestamp_tolerance_seconds` (default 300) and per-field integer `numeric_exchange_tolerances` configure matching. Outcomes retain a reason code and counterpart evidence. Missing or mismatched counterparts remain review findings unless `require_counterpart: true` is explicitly configured.
- Cabrillo exchange tokens map to semantic exchange fields in the configured exchange-rule order only when the token count matches; otherwise the submitted raw exchange is retained for review and the scorer does not guess a mapping. ADIF standard exchange fields (for example `MY_GRIDSQUARE`/`GRIDSQUARE`, `STX`/`SRX`, and `RST_SENT`/`RST_RCVD`) map to matching semantic values; source fields remain preserved.
- Rules that consume `entity`, `cq_zone`, `itu_zone`, or `continent` require a `cty` version pinned for the contest-start instant. Each score run records all contest pins used. If a required pin is missing or invalid, scoring fails with the dataset key rather than falling back to the latest active version.
- Domain scoring returns pending structured workflow actions for publication and award consumers. These are handoff requests for trusted services, not dynamically loaded user code.
- Saving and activating rulesets is a privileged contest-manager operation. Ruleset definitions are immutable versions, and every selection change is recorded in append-only contest activation history. Current API authentication enforcement is completed in Phase 5.

## Versioning

Additive, backward-compatible fields and endpoints remain in the current API version. Removing or changing field meaning, response shape, or behavior incompatibly requires a new `/api/vN` route prefix and a documented deprecation/migration period. OpenAPI is the machine-readable contract for each version.

Operational setup and recovery are documented in the [operator guide](../operations/README.md). The precise imported Cabrillo and ADI/ADIF subsets and current exports are listed in [supported formats](../formats/README.md).
