# Master data sources and nightly refresh

Contestmaster designates Big CTY `cty.dat` as the **primary operational source for master-data imports** and callsign resolution. Use it first for the shared contest-facing entity, prefix, CQ-zone, and amateur-radio ITU-zone mappings. The other sources in this catalog validate those mappings or fill data that `cty.dat` does not provide, including IARU regions, sovereign country/area identifiers, and jurisdiction-specific call districts. Published contest rules and their governing organizations remain authoritative when interpreting contest results.

These datasets serve different contest rule systems and should be kept in separate tables. “Public source” describes access to the material; it does not automatically grant permission to copy, transform, or redistribute it. Confirm source terms before enabling an importer for a public service.

For each enabled external dataset used in the application, retain its applicable license or use-terms URL in the source inventory. The Vue application footer must identify each such dataset and link directly to those terms on every page. Do not list datasets that the hosted service is prohibited from using, including the excluded ARRL DXCC list.

### Source selection conclusions

- CQ and amateur ITU zone definitions are published by different authorities and must never share one zone table or numeric namespace.
- Big CTY is the permitted primary operational import source for callsign prefixes, DXCC mappings, CQ-zone, and amateur-radio ITU-zone mappings; preserve the applicable license notice. The ARRL DXCC list is excluded from the hosted service indefinitely. Official zone references and each contest's published rules govern adjudication.
- IARU Region membership and ITU Radio Region geography are related, but model them separately and keep their correspondence explicit.
- “Country” is too imprecise for contest scoring. A master entity should carry a namespace and authority code so DXCC entities, sovereign countries, territories, and contest-specific entities are not collapsed together.
- ITU Appendix 42 allocates international call-sign series to administrations. It does not by itself describe every domestic callsign pattern, issued station, contest prefix, or call district.
- Call districts must be maintained per administration. Some districts may be inferred from a callsign only under a jurisdiction's published plan; in other cases the station's operating location is required.
- At launch, every jurisdiction included in call-district support must have an official machine-readable regulator source integrated. Keep this coverage explicit per jurisdiction and out of scope where no suitable source or permitted use exists.
- Every row or assignment should retain source/version provenance and effective dates. Keep removed items for historical log interpretation and reproducible score runs.

## Nightly refresh behavior

The importer enables Big CTY and the FCC ULS U.S. call-district source. The Big CTY adapter follows its official RSS feed to the latest dated release page, verifies the dated ZIP link, extracts `cty.dat` and its included copyright notice, validates the complete file, and imports entity, prefix, exact-callsign, CQ-zone, amateur ITU-zone, continent, coordinate, and UTC-offset data into version-scoped ORM tables. The FCC adapter first verifies the license in the official machine-readable catalog, then reads the complete amateur-license archive, aggregates only distinct call-area digits, and does not retain callsigns or licensee data. U.S. call-area coverage is the only call-district coverage currently configured; bulk archive ingestion must be verified in deployment before it can be treated as operationally available. Other listed sources remain recommendations until their terms and adapters are reviewed; do not treat their presence in this catalog as an enabled feed. Phase 3 remains incomplete until suitable country/area and IARU/ITU Radio Region sources and every launch-supported call-district jurisdiction are integrated.

Use `uv run contestmaster-master-data sync` for a one-shot import of both enabled sources; use `sync-cty` or `sync-fcc` for a single adapter, and `status` to inspect versions and recent runs. The API runs enabled imports on startup when either required active version is absent and checks nightly at 02:00 UTC by default. Each source is isolated so its failure does not suppress another source or replace the last good version. `MASTER_DATA_SCHEDULER_ENABLED` and `MASTER_DATA_NIGHTLY_HOUR_UTC` configure this single-process timer. A database partial unique index prevents overlapping source/dataset runs across the API and CLI. Fetching and parsing happen before the version transaction; a failed response records a failed run and leaves the active version unchanged.

Sync runs use `status=succeeded` and `change_detected=false` as the auditable no-change outcome. The version checksum covers normalized parsed data; the run checksum covers the downloaded archive. A meaningful existing-prefix entity/zone reassignment creates a candidate and leaves the current version active for administrator review. A successful safe update closes the old effective interval and starts the new one at retrieval time.

Schedule a master-data source check every night. For each configured source:

1. Fetch the official landing page or data feed, honoring published access limits and terms. Use ETag/Last-Modified where supported; otherwise compare a normalized content checksum or publication/version date.
2. Store the response metadata and raw artifact when permitted: source key and URL, retrieval timestamp, published edition/date, checksum, parser version, and license/use note.
3. Parse to a candidate dataset and validate required keys, record counts, uniqueness, cross-table references, effective dates, and expected coverage. Compute a canonical checksum from the normalized parsed content.
4. Keep the active version if retrieval, parsing, validation, licensing, or completeness checks fail. Record the failure and alert operators.
5. If a dataset checksum matches its current version, record a successful sync with `change_detected=false` and do not create a `MasterDataVersion` or move any effective-time boundary. Activate a new version only when validated normalized content changes. Its validity interval is half-open: `[valid_from, valid_to)`. On activation, close the previous version's interval at the new version's `valid_from`. Material changes to human-authored geographic definitions or sources that require interpretation should wait for review; a nightly check can discover changes without assigning zones incorrectly.
6. Retain prior versions and pin each contest to the version of every required dataset whose validity interval contains the contest's start instant. The interval includes `valid_from` and excludes `valid_to`. Select the version after contest start, based on the historical interval, even if scoring occurs later. Persist the selected dataset/version pairs on the contest and on each score run; never resolve against whichever version happens to be active at scoring time. If there is no version covering contest start for a required dataset, block dependent scoring and report the missing dataset rather than falling back to a newer version.
7. Allow a global-administrator-only web section to list versions and sync provenance, activate validated candidates, and delete old versions only when they are not current and have no contest, score-run, QSO-resolution, or other retained-record references. Enforce role checks in the API and deletion restrictions in the API/database as well as by disabling the UI action. Retain referenced versions to preserve contest interpretation and reproducible historical results.

The nightly schedule means each enabled source is checked every night; it does not mean every source is guaranteed to publish new data nightly. Static authoritative references may be unchanged for years. A no-change check is still an auditable sync run, but it must not create a duplicate version. A source with restrictive terms must stay disabled for copying/redistribution until the appropriate permission is in place.

## Contest-time version selection and administration

Treat `MasterDataVersion.valid_from` and `valid_to` as UTC instants defining a half-open validity interval. For each dataset required by a contest, select the single version where `valid_from <= contest.starts_at` and (`valid_to IS NULL` or `contest.starts_at < valid_to`). Pin those dataset/version pairs to the contest after its start instant and use that pinned set for all its later adjudication and score runs. Do not choose a version by score-run time or silently use the latest version when a time-matching version is missing.

The Vue administration area for master-data versions is global-administrator-only, with every API endpoint enforcing the same role. Show version identity, dataset, effective interval, source/release, checksum, sync outcome, and references. Permit deletion only for old non-current versions with no contest, score-run, QSO-resolution, or other retained-record references; reject deletion server-side if a reference exists. Deletion must also follow source-artifact retention terms and leave sync/audit metadata that does not compromise historical score evidence.

- [IARU Region 1 HF Manager's Handbook v9](https://www.iaru-r1.org/wp-content/uploads/2019/08/hf_managers_handbook_v9.pdf) identifies its edition date and non-commercial copying terms on its cover page.
